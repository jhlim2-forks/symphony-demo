# 설계

## 구조

- 저장소 루트의 단일 Go 모듈(`module todo`)로 두고, Go 표준 라이브러리와 HTML/CSS/JavaScript만 사용합니다.
- 서버는 `go run .`으로 실행하며 `-listen` 플래그(기본값 `127.0.0.1:8091`)로 주소를 받습니다.
- 서버는 두 가지 일을 합니다.
  - `/` 요청에 `index.html` 한 파일을 제공합니다.
  - `/api/todos`에서 할 일 목록 조회와 추가를 JSON으로 처리합니다.
- 할 일은 서버 메모리의 목록 하나에 추가한 순서대로 담습니다. 식별자는 1부터 시작해 추가할 때마다 1씩 커지는 정수입니다.
- 할 일 하나는 식별자, 제목, 마감일을 가집니다. 마감일은 `YYYY-MM-DD` 문자열이거나 없음이며, 없음은 JSON에서 `null`로 나타냅니다. 날짜 계산을 하지 않으므로 날짜 자체를 값으로 변환해 두지 않고, 검사를 통과한 입력 문자열을 그대로 보관합니다.
- 마감일 검사는 표준 라이브러리의 날짜 파싱(`time.Parse`에 `2006-01-02` 형식)으로 합니다. 글자 형식 검사와 달력 존재 여부 검사를 나눠서, 형식이 틀린 경우와 날짜가 없는 경우에 서로 다른 오류 문장을 돌려줍니다.
- 목록은 여러 요청이 동시에 들어와도 안전하도록 잠금으로 보호합니다.
- 저장소가 메모리이므로 서버 프로세스가 끝나면 목록도 함께 사라집니다.

## API

`docs/requirements.md`의 `## API 계약`에 적은 계약을 그대로 따릅니다.

| 메서드와 경로 | 하는 일 | 성공 응답 | 실패 응답 |
| --- | --- | --- | --- |
| `GET /` | 한 페이지 화면 제공 | `200` + HTML | — |
| `GET /api/todos` | 할 일 목록을 추가한 순서대로 돌려줌 | `200` + `{"todos":[{"id":1,"title":"...","dueDate":"2026-10-31"}, ...]}` | — |
| `POST /api/todos` | 할 일 추가(마감일은 선택) | `201` + `{"id":1,"title":"...","dueDate":"2026-10-31"}` 또는 `"dueDate":null` | `400` + `{"error":"..."}` |
| 그 밖의 메서드로 `/api/todos` | 처리하지 않음 | — | `405` + `{"error":"..."}` |

제목 검사 순서는 다음과 같습니다.

1. 요청 본문을 JSON으로 읽습니다. 읽을 수 없거나 본문이 비어 있거나 `title`이 문자열이 아니면 `400`이며 메시지는 `요청 형식이 올바르지 않습니다.`입니다.
2. `title`의 앞뒤 공백을 제거합니다.
3. 결과가 빈 문자열이면 `400`이며 메시지는 `제목을 입력해 주세요.`입니다. `title` 항목이 아예 없는 경우도 빈 문자열로 봅니다.
4. 결과의 글자 수가 200자를 넘으면 `400`이며 메시지는 `제목은 200자까지 입력할 수 있습니다.`입니다. 글자 수는 유니코드 코드 포인트 개수(Go의 `[]rune` 길이)로 세며, 결합 문자나 이모지 조합도 코드 포인트마다 1자로 셉니다.
5. 제목 검사를 모두 통과하면 아래 마감일 검사로 넘어갑니다.

마감일 검사 순서는 제목 검사 다음입니다. 제목과 마감일이 함께 잘못된 요청은 제목 오류 문장을 먼저 돌려줍니다.

1. `dueDate` 항목이 없거나 `null`이면 마감일 없음으로 정하고 바로 7번으로 갑니다.
2. `dueDate`가 문자열이 아니면 `400`이며 메시지는 `요청 형식이 올바르지 않습니다.`입니다.
3. 빈 문자열(`""`)이면 마감일 없음으로 정하고 7번으로 갑니다. 공백만 있는 문자열은 빈 문자열로 보지 않고 다음 검사로 넘깁니다.
4. 글자 형식을 봅니다. 길이가 정확히 10자이고 `숫자 4개`-`숫자 2개`-`숫자 2개`(ASCII 숫자와 하이픈) 꼴이 아니면 `400`이며 메시지는 `마감일은 YYYY-MM-DD 형식으로 입력해 주세요.`입니다. 앞뒤 공백은 제거하지 않으므로 공백이 붙은 값은 이 단계에서 걸립니다.
5. 형식이 맞으면 `time.Parse("2006-01-02", 값)`으로 달력에 있는 날짜인지 봅니다. 파싱이 실패하면 `400`이며 메시지는 `달력에 없는 날짜입니다. 다시 확인해 주세요.`입니다.
6. 파싱 결과를 다시 `2006-01-02` 형식으로 적은 문자열이 입력과 다르면 같은 `달력에 없는 날짜입니다. 다시 확인해 주세요.` 메시지로 거절합니다. 날짜가 조용히 보정되어 들어오는 일을 막는 확인입니다.
7. 모두 통과하면 제목과 마감일(없으면 `null`)을 담아 목록 끝에 추가하고 `201`로 추가 결과를 돌려줍니다.

실패 응답 본문은 모두 `{"error":"..."}` 한 가지 형태이며, 문장은 `docs/requirements.md`의 `## API 계약`에 적은 다섯 가지(그리고 `405`의 `지원하지 않는 요청 방식입니다.`)만 사용합니다. UI는 이 문장을 그대로 보여 줍니다.

## UI

`index.html` 한 파일로 만듭니다. 모든 문구는 한국어입니다.

- 머리글: `할 일 목록`
- 추가 영역: 제목 입력 칸(안내 문구 `할 일을 입력하세요`), 마감일 입력 칸, `추가` 버튼
- 마감일 입력 칸: `type="date"`인 입력 요소 하나(`id="due-date"`)를 제목 입력 칸 옆에 두고, 보조 설명은 `마감일(선택)`으로 적습니다. 비워 둘 수 있으며, 비어 있으면 `POST /api/todos` 본문의 `dueDate`에 빈 문자열을 그대로 담아 보냅니다. `type="date"` 입력 칸의 값은 브라우저가 `YYYY-MM-DD`로 주므로 화면에서 형식을 따로 바꾸지 않습니다. 추가가 성공하면 제목 입력 칸과 함께 이 칸도 비웁니다.
- 목록 영역: 할 일을 추가한 순서대로 위에서 아래로 나열합니다. 항목 한 줄은 제목 글자를 담은 요소와 마감일을 담은 요소(`class="due-date"`)로 나누고, 마감일 요소에는 `마감일 2026-10-31`처럼 `마감일 ` 뒤에 `YYYY-MM-DD` 날짜를 글자로 적습니다. 받아 온 `dueDate`가 `null`이면 마감일 요소를 만들지 않아 아무것도 보이지 않습니다. 제목과 마감일은 모두 글자로만 넣습니다.
- 빈 목록 안내 영역: 목록 자리(목록 영역 바로 아래)에 할 일 항목과 분리된 문단 요소 하나(`id="empty-message"`)를 마크업으로 두고, 그 안에 `아직 할 일이 없으니 위 입력 칸에서 첫 할 일을 추가해 보세요.`를 글자로 적어 둡니다. 기본 상태는 `hidden`이며, 목록을 그릴 때마다 받아 온 할 일 수가 0이면 `hidden`을 풀어 보여 주고 1 이상이면 다시 `hidden`으로 숨깁니다. 문구는 `index.html`에만 두고 API 응답에서 받아 오지 않습니다.
- 오류 영역: 추가가 거절되면 서버가 준 `error` 문장을 입력 칸 아래에 보여 주고, 다음 추가가 성공하면 지웁니다. 오류 영역의 동작은 이번에 바꾸지 않으며, 빈 목록 안내 영역은 오류 여부가 아니라 받아 온 할 일 수만 보고 표시 여부를 정합니다.
- 동작: 화면을 열면 `GET /api/todos`로 목록을 받아 그립니다. `추가` 버튼을 누르거나 입력 칸에서 Enter를 누르면 제목과 마감일 입력 칸의 값을 `{"title":...,"dueDate":...}`로 담아 `POST /api/todos`를 호출하고, 성공하면 두 입력 칸을 비우고 목록에 새 할 일을 더해 그립니다. 목록을 그리는 함수 하나가 항목 나열과 빈 목록 안내 영역의 표시 여부를 함께 정하므로, 첫 할 일을 추가하면 화면을 다시 열지 않아도 안내 문구가 사라집니다.

## 수용 기준

- **REQ-01** `GET /`가 `200`과 HTML을 돌려주고, 그 화면에 제목 입력 칸과 `추가` 버튼, 할 일 목록 영역이 한국어로 들어 있다.
- **REQ-02** `POST /api/todos`에 `{"title":"회의 자료 준비"}`를 보내면 `201`과 함께 `id`가 `1`이고 `title`이 `회의 자료 준비`인 응답을 돌려주고, 이어서 `GET /api/todos`를 호출하면 그 할 일이 목록에 들어 있다. 본문이 올바른 JSON이 아닌 경우(예: `{"title":`)와 `title`이 문자열이 아닌 경우(예: `{"title":123}`)에는 `400`과 `{"error":"요청 형식이 올바르지 않습니다."}`를 돌려주고 `GET /api/todos`의 목록 길이가 호출 전과 같다.
- **REQ-03** `POST /api/todos`에 `{"title":""}`, `{"title":"   "}`, `{}`를 보내면 각각 `400`과 `{"error":"제목을 입력해 주세요."}`를 돌려주고, `GET /api/todos`의 목록 길이가 호출 전과 같다.
- **REQ-04** 앞뒤 공백을 제거한 제목의 코드 포인트 수가 200일 때는 `201`로 추가되고, 201일 때는 `400`과 `{"error":"제목은 200자까지 입력할 수 있습니다."}`를 돌려주며 `GET /api/todos`의 목록 길이가 호출 전과 같다. 다음 사례로 계산 기준을 확인한다.
  - 한글 `가` 200번 반복(600바이트)은 `201`, 201번 반복은 `400`이다. 즉 바이트 수로 세지 않는다.
  - 앞뒤에 공백을 붙인 `" " + 한글 200자 + " "`는 `201`이고, 저장된 `title`에는 앞뒤 공백이 없다.
  - `e`+`◌́`(U+0065 U+0301) 쌍을 100번 반복한 제목은 코드 포인트 200개이므로 `201`이고, 101번 반복(코드 포인트 202개)은 `400`이다. 즉 눈에 보이는 글자 수가 아니라 코드 포인트 수로 센다.
- **REQ-05** 할 일 세 건을 차례로 추가한 뒤 `GET /api/todos`를 호출하면 `todos` 배열의 제목이 추가한 순서와 같다.
- **REQ-06** 새로 만든 서버에 `GET /api/todos`를 호출하면 `todos`가 빈 배열이다.
- **REQ-07** `GET /`가 돌려주는 HTML에 `id="empty-message"` 요소가 있고, 그 요소에 `아직 할 일이 없으니 위 입력 칸에서 첫 할 일을 추가해 보세요.` 문구가 그대로 들어 있다. 할 일이 없는 서버에 `GET /api/todos`를 호출하면 `todos`는 빈 배열이고 응답 본문에 이 문구가 들어 있지 않다.
- **REQ-08** 브라우저에서 아래 절차를 그대로 따라가 화면에 보이는 것으로 확인한다.
  1. 할 일이 없는 서버를 켜고 `/`를 열면 목록 자리에 `아직 할 일이 없으니 위 입력 칸에서 첫 할 일을 추가해 보세요.`가 보이고, 할 일 항목은 한 줄도 보이지 않는다.
  2. 같은 화면에서 입력 칸에 `회의 자료 준비`를 적고 `추가`를 누르면, 화면을 다시 열지 않은 상태에서 안내 문구가 사라지고 목록에 `회의 자료 준비` 한 줄이 보인다.
  3. 이어서 `메일 답장`을 추가해도 안내 문구는 계속 보이지 않고, 목록에는 두 줄이 추가한 순서대로 보인다.
  4. 1번 상태(목록이 빈 상태)에서 빈 제목으로 `추가`를 눌러 거절되면 목록이 그대로 비어 있으므로 안내 문구가 계속 보인다. 2번 상태(할 일 한 건)에서 같은 방식으로 거절되면 목록이 비어 있지 않으므로 안내 문구는 보이지 않는다.
  5. 화면을 새로 고치면 그때의 할 일 수에 따라 1번(0건)과 2번(1건 이상)의 보임새가 그대로 다시 나타난다.
  - 서버 쪽으로는 `GET /`가 돌려주는 HTML에 기본 상태가 `hidden`인 `id="empty-message"` 요소가 있고, `POST /api/todos`로 할 일 하나를 추가한 뒤 `GET /api/todos`의 `todos` 길이가 1이며, 거절되는 제목(예: `{"title":""}`)을 보낸 뒤에는 길이가 0임을 확인한다. 화면에서 문구가 실제로 보이고 숨는지는 위 1~5번 절차로 확인한다.
- **REQ-09** `GET /`가 돌려주는 HTML의 맨 아래(목록 영역 다음)에 `할 일은 이 서버에만 잠시 보관되며, 서버를 다시 켜면 사라집니다.` 문구가 그대로 들어 있고, 할 일이 있든 없든 늘 보인다.
- **REQ-10** `POST /api/todos`에 `{"title":"회의 자료 준비","dueDate":"2026-10-31"}`를 보내면 `201`과 `{"id":1,"title":"회의 자료 준비","dueDate":"2026-10-31"}`를 돌려주고, 이어서 `GET /api/todos`를 호출하면 그 할 일의 `dueDate`가 `2026-10-31`이다. 돌려준 마감일에는 시각이나 시간대가 붙지 않으며 보낸 문자열과 글자까지 같다. `2024-02-29`(윤년)도 같은 방식으로 `201`로 추가된다.
- **REQ-11** 아래 세 요청이 모두 `201`을 돌려주고, 각 응답과 이어지는 `GET /api/todos`에서 그 할 일의 `dueDate`가 `null`이다.
  - `{"title":"메일 답장"}` (`dueDate` 항목 없음)
  - `{"title":"메일 답장","dueDate":null}`
  - `{"title":"메일 답장","dueDate":""}`
- **REQ-12** `POST /api/todos`에 `{"title":"회의 자료 준비","dueDate":"2026-1-5"}`, `{"title":"회의 자료 준비","dueDate":"2026/10/31"}`, `{"title":"회의 자료 준비","dueDate":"20261031"}`, `{"title":"회의 자료 준비","dueDate":"2026-10-31T00:00:00Z"}`, `{"title":"회의 자료 준비","dueDate":"31-10-2026"}`, `{"title":"회의 자료 준비","dueDate":" 2026-10-31 "}`, `{"title":"회의 자료 준비","dueDate":"내일"}`를 보내면 각각 `400`과 `{"error":"마감일은 YYYY-MM-DD 형식으로 입력해 주세요."}`를 돌려주고, `GET /api/todos`의 목록 길이가 호출 전과 같다. `{"title":"회의 자료 준비","dueDate":20261031}`처럼 `dueDate`가 문자열도 `null`도 아니면 `400`과 `{"error":"요청 형식이 올바르지 않습니다."}`를 돌려준다. 제목과 마감일이 함께 잘못된 `{"title":"","dueDate":"2026-1-5"}`는 `400`과 `{"error":"제목을 입력해 주세요."}`를 돌려준다.
- **REQ-13** `POST /api/todos`에 `{"title":"회의 자료 준비","dueDate":"2026-02-30"}`, `{"title":"회의 자료 준비","dueDate":"2026-02-29"}`, `{"title":"회의 자료 준비","dueDate":"2026-04-31"}`, `{"title":"회의 자료 준비","dueDate":"2026-13-01"}`, `{"title":"회의 자료 준비","dueDate":"2026-00-10"}`, `{"title":"회의 자료 준비","dueDate":"2026-10-00"}`를 보내면 각각 `400`과 `{"error":"달력에 없는 날짜입니다. 다시 확인해 주세요."}`를 돌려주고, `GET /api/todos`의 목록 길이가 호출 전과 같다. 같은 날짜가 다음 달로 넘어간 날짜(예: `2026-03-02`)로 바뀌어 추가되는 일도 없다.
- **REQ-14** 마감일이 있는 할 일과 없는 할 일을 차례로 추가한 뒤 `GET /api/todos`를 호출하면 `todos`의 각 항목에 `id`, `title`, `dueDate` 세 항목이 모두 들어 있고, 마감일을 지정한 항목은 `"2026-10-31"`, 지정하지 않은 항목은 `null`이다. 마감일이 없는 항목에서도 `dueDate` 항목 자체는 응답에서 빠지지 않는다.
- **REQ-15** 브라우저에서 아래 절차를 그대로 따라가 화면에 보이는 것으로 확인한다.
  1. 마감일 `2026-10-31`을 넣어 `회의 자료 준비`를 추가하면 목록의 그 줄에 제목과 함께 `마감일 2026-10-31`이 보인다.
  2. 마감일을 비워 둔 채 `메일 답장`을 추가하면 그 줄에는 제목만 보이고 마감일 글자는 보이지 않는다.
  3. 화면을 새로 고쳐도 두 줄의 보임새가 그대로 다시 나타난다.
  - 서버 쪽으로는 위 두 할 일을 추가한 뒤 `GET /api/todos`의 `todos`가 각각 `dueDate` `"2026-10-31"`과 `null`을 담고 있음을 확인한다. `GET /`가 돌려주는 HTML에는 `마감일 `을 붙여 날짜를 적는 목록 그리기 코드와 `class="due-date"`가 들어 있다.
- **REQ-16** `GET /`가 돌려주는 HTML에 `type="date"`이고 `id="due-date"`인 입력 요소와 `마감일(선택)` 설명이 들어 있다. 브라우저에서 마감일 칸을 비운 채 제목만 적고 `추가`를 누르면 할 일이 추가되고 그 줄에 마감일이 보이지 않으며, 마감일 칸에 날짜를 넣어 추가하면 추가가 성공한 뒤 제목 칸과 마감일 칸이 모두 비어 있다.

## 위험

- 메모리 저장이므로 서버를 다시 켜면 입력한 할 일이 사라집니다. 첫 버전에서 받아들이는 제약이며, 화면에도 데이터가 유지된다는 기대를 주는 문구를 두지 않습니다.
- 200자 한도를 바이트 수로 세면 한글 제목이 70자 정도에서 막힙니다. 유니코드 코드 포인트 수로 세어 이를 피합니다. 결합 문자나 이모지 조합은 보이는 것보다 많은 글자로 세지지만, 표준 라이브러리만으로 사용자 인식 글자 수를 세기는 어려워 첫 버전에서는 코드 포인트 기준으로 둡니다.
- 입력한 제목을 화면에 그릴 때 HTML로 해석하면 의도하지 않은 내용이 실행될 수 있습니다. 제목은 항상 글자로만 넣습니다.
- 여러 탭에서 동시에 추가하면 한 탭의 화면이 오래된 목록을 보여 줄 수 있습니다. 첫 버전은 화면을 다시 열어 맞추는 수준으로 둡니다.
- 빈 목록 안내 문구를 화면과 서버 응답 두 곳에서 관리하면 문구가 서로 어긋날 수 있습니다. 문구는 `index.html` 한 곳에만 두고 API 응답 형식은 그대로 둡니다.
- 화면에서 안내 문구가 보이고 숨는 동작은 표준 라이브러리 테스트만으로는 브라우저와 똑같이 재현할 수 없습니다. 자동 검사로는 화면 파일에 담긴 문구와 서버 응답까지만 확인하고, 실제 보임새는 수용 기준의 재현 절차를 따라가 확인합니다.
- 안내 문구를 목록 항목과 같은 방식으로 그리면 할 일이 하나도 없는 상태를 할 일 한 건처럼 보여 줄 수 있습니다. 항목 나열과 분리된 요소 하나에 담아 이를 피합니다.
- 윤년과 달마다 다른 날짜 수를 직접 계산하면 틀리기 쉽습니다. 표준 라이브러리의 날짜 파싱에 맡기고, 파싱 결과를 다시 글자로 적어 입력과 같은지 확인해 `2026-02-30`이 `2026-03-02`처럼 조용히 보정되는 일을 막습니다.
- 마감일에 시간대가 없으므로 같은 날짜라도 사람마다 서버마다 뜻하는 순간이 다를 수 있습니다. 날짜를 비교하거나 계산하는 동작을 두지 않고 입력한 날짜를 그대로 보관해 보여 주는 수준으로 한정합니다.
- `type="date"` 입력 칸은 브라우저가 달력으로 날짜를 고르게 해 주지만, 이 칸을 지원하지 않는 브라우저나 API를 직접 호출하는 경우에는 아무 글자나 들어올 수 있습니다. 화면 입력 방식에 기대지 않고 서버에서 형식과 달력 존재 여부를 모두 검사합니다.
- 응답에 `dueDate` 항목이 늘어나므로 화면이 이 항목을 읽지 못하면 마감일이 빈칸으로만 보일 수 있습니다. 목록을 그리는 함수 한 곳에서 제목과 마감일을 함께 그려 두 값이 어긋나지 않게 합니다.
- 마감일을 지역 설정에 맞춰 다른 형식으로 바꿔 보여 주면 서버가 보관한 값과 화면에 보이는 값이 달라져 혼동을 줄 수 있습니다. 보관한 `YYYY-MM-DD`를 그대로 보여 줍니다.
